# cloud-init

🟡 Good to Know · Relevant for: DevOps · Cloud · Platform

> **TL;DR:** `cloud-init status` reports whether first-boot configuration finished successfully;
> `cloud-init analyze show` breaks down how long each stage took; `cloud-init clean` resets state
> so an image can be reused to launch a fresh instance.

## Purpose

`cloud-init` (the CLI) inspects, debugs, and resets the same-named service that applies a cloud
instance's first-boot configuration — see [cloud-init](../docs/25-linux-for-cloud/cloud-init.md)
for the full concept and the YAML user-data format it consumes.

## Syntax

```
cloud-init COMMAND [OPTIONS]
```

## Arguments

| Argument | Meaning | Required |
|---|---|---|
| `COMMAND` | The subcommand to run (`status`, `analyze`, `clean`, `init`, `modules`) | Yes |

## Options

| Command | Flag | Meaning |
|---|---|---|
| `status` | `--wait` | Block until `cloud-init` finishes running, then report status |
| `status` | `--long` | Show detailed status including which stage is active |
| `analyze` | `show` | Break down time spent in each boot stage |
| `analyze` | `blame` | List individual config modules sorted by time taken, slowest first |
| `clean` | `--logs` | Also remove `cloud-init`'s log files, not just its cached state |
| `clean` | `--reboot` | Reboot immediately after cleaning, re-running `cloud-init` from scratch |

## Examples

```
$ cloud-init status
```
Report whether `cloud-init` has finished running and whether it succeeded.

```
$ cloud-init status --wait
```
Block until `cloud-init` finishes — useful in automation before proceeding with a health check.

```
$ cloud-init analyze show
```
Show total time spent in each of `cloud-init`'s four boot stages.

```
$ cloud-init analyze blame
```
List the slowest individual configuration modules, useful for diagnosing a slow boot.

```
$ sudo cloud-init clean --logs
```
Reset `cloud-init`'s state and logs, typically run before converting a configured instance back
into a reusable image (see [Auto-Scaling and Custom Linux Images](../docs/25-linux-for-cloud/auto-scaling-and-custom-linux-images-amis.md)).

## Expected Output

```
$ cloud-init status
status: done

$ cloud-init analyze show
-- Boot Record 01 --
The total time elapsed since completing an event is 12.443 seconds

Startup finished in 3.201 seconds (kernel) + 9.242 seconds (userspace) = 12.443 seconds
```

## Exit Status

`0` if the queried command succeeds; `cloud-init status` specifically returns non-zero if
`cloud-init` itself ended in an error state, distinct from the exit code of the `status` command
call.

## Common Errors

| Symptom | Cause | Fix |
|---|---|---|
| `status: error` | A module in user-data failed (invalid YAML, a `runcmd` command failed) | Check `/var/log/cloud-init.log` and `/var/log/cloud-init-output.log` for the specific failure |
| `status: disabled` | `cloud-init` was explicitly disabled on this image | Confirm this is intentional; re-enable if the instance was expected to self-configure |
| Configuration didn't apply after a reboot | Not a `cloud-init` error — by default it does not rerun on every boot, only on genuinely new instances | Use `cloud-init clean --reboot` if a full rerun is genuinely needed for testing |

## Security Considerations

User-data can contain sensitive values (SSH keys, initial credentials) and is often retrievable
from the instance metadata service by anything running on the instance — avoid placing long-lived
secrets directly in user-data; prefer injecting them via a secrets manager or
[IAM instance role](../docs/25-linux-for-cloud/iam-and-instance-roles.md) at runtime instead.

## Performance Considerations

`cloud-init analyze blame` is the standard tool for diagnosing a slow-booting custom image — a
single slow `runcmd` step (e.g. a large package install) is a common and easily identified cause.

## Production Usage

Production teams rarely write ad hoc user-data by hand for every launch — it's generated by
infrastructure-as-code tooling (Terraform, covered in Module 26) from a template, and
`cloud-init status --wait` is commonly used as a readiness gate in automated deployment pipelines
before an instance is added to a load balancer.
